Compact 系统概述

对话式 AI 工具管理长对话上下文的核心机制。对比 Claude Code 与 Pi-mono 的压缩策略，提出 ys-code 的混合实现路径。

现状说明： ys-code 当前未实现 Compact 系统。消息纯内存存储（Agent._state.messages），无持久化、无会话恢复、无压缩。
背景与定位 核心原理 源码实现 对比分析 借鉴建议 实现路径

背景与定位

Compact（上下文压缩）系统是对话式 AI 工具管理长对话上下文的核心机制。当对话 Token 数量接近模型上下文窗口限制时，系统通过压缩历史消息为摘要来释放上下文空间，确保对话能持续进行而不丢失关键信息。

核心问题

长对话中，消息历史会线性增长，最终耗尽模型的上下文窗口（通常 100K-200K tokens）。若无压缩机制，对话将在数十轮后无法继续。

核心原理

Claude Code 架构：多级压缩

Claude Code 采用从轻到重的渐进策略：

microCompact → 轻量级清理，Time-based + Cached MC
sessionMemoryCompact → 实验性会话记忆压缩
compactConversation 全量压缩，Forked Agent 缓存复用

触发条件： 当 tokenCount >= contextWindow - 33,000 时触发（预留 20K 输出 + 13K 缓冲）。

关键设计：Forked Agent 缓存复用实现 98% 命中率；连续 3 次失败后熔断停止自动压缩。

Pi-mono 架构：单一全量压缩

基于树形会话结构的压缩策略：

  • 触发条件：contextTokens > contextWindow - reserveTokens（默认预留 16,384）
  • 核心流程：prepareCompaction → findCutPoint → generateSummary → SessionManager 追加
  • 关键设计：原生支持分支摘要、迭代更新前一个摘要、累积文件追踪

可借鉴点与建议

建议对齐 Claude Code

特性 优先级 说明
多级压缩策略 P1 microCompact → full compact 的渐进策略减少全量压缩频率
Forked Agent 缓存复用 P1 复用 prompt cache 可显著降低压缩成本和延迟
熔断机制 P2 防止不可恢复场景下无限重试
附件保留策略 P2 压缩后重新注入关键文件和技能上下文
PTL 重试机制 P2 压缩请求本身超长时的优雅降级

建议对齐 Pi-mono

特性 优先级 说明
树形会话结构 P1 原生支持分支和分支摘要，为后续 /tree 命令打基础
迭代摘要 P2 基于前一个摘要增量更新，保持连贯性
累积文件追踪 P2 跨多次压缩累积文件操作，避免重复读取
简洁实现 P2 4 个文件 ~1,350 行，适合 MVP 快速落地

推荐实现路径

核心建议

采用 Pi-mono 风格树形结构 + Claude Code 多级压缩策略 的混合方案。

Phase 1 → Pi-mono 风格持久化（JSONL + 树 + 内存构建）
Phase 2 → 基于持久化的 Compact（自动/手动触发 + 迭代摘要）
Phase 3 → 引入 Claude Code 风格的多级压缩（microCompact + 缓存复用）
Phase 4 如果会话文件变大，引入分块截断读取优化

Phase 1 核心工作量

  • 定义 SessionEntry 类型体系（header + message + compaction + ...）
  • 实现 SessionManager 类（加载/追加/构建 context）
  • 将 AgentSession 的消息存储从内存数组改为 SessionManager
  • 添加 --resume 或自动恢复最近会话的能力

Phase 2 核心工作量

  • Token 估算函数
  • 压缩触发判断（阈值计算）
  • 摘要生成（调用 LLM）
  • CompactionEntry 写入 + buildSessionContext 处理 compaction
